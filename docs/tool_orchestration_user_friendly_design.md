# 面向小白用户的算法流程编排设计方案

## 设计目标

`tool_orchestration_agent` 不应该只输出一条专业的算法链路，例如：

```text
人员检测 -> 姿态识别 -> 行为判断 -> 告警输出
```

对小白用户来说，这种链路存在几个问题：

1. 不知道每一步是干什么的。
2. 不知道这一步是不是必须的。
3. 不知道能不能换。
4. 不知道换了以后有什么影响。
5. 不知道该怎么表达修改需求。

因此，`tool_orchestration_agent` 应该从“执行链路的智能体”升级为：

> 算法流程导购员 + 编排解释员 + 修改顾问

核心目标是：

> 让用户看得懂每一步，知道每一步能不能改，知道有哪些替代方案，并且能用自然语言完成修改。

---

## 一、用户看到的流程应该是“任务流程”

专业流程可能是：

```text
YOLOv8-person -> DeepSORT -> PoseEstimator -> RuleEngine -> AlertService
```

小白用户应该看到的是：

```text
识别画面里有没有人
    ↓
持续跟踪这个人
    ↓
判断这个人的动作
    ↓
确认是否触发告警
    ↓
输出告警结果
```

每个节点都应该包含三层信息。

### 1. 小白解释

例如“人员检测”节点：

> 这一步的作用是先从画面里找出人。后面的动作分析、行为判断都依赖它。如果这一步找不到人，后面就没法继续判断。

### 2. 技术说明

给懂一点技术的人看：

> 当前使用目标检测模型识别人体框，输出人员位置、置信度和截图区域。

### 3. 可修改提示

告诉用户它能不能改：

> 这一步可以替换。你可以选择更快、更准、成本更低，或者更适合特殊场景的识别方式。

---

## 二、每个流程节点都应该有“可替换性等级”

不是所有步骤都适合让用户随便换。建议给每个节点标一个修改等级。

| 等级 | 含义 | 示例 |
|---|---|---|
| 可自由替换 | 可以给用户多个替代方案 | 人员检测模型、车辆检测模型、烟雾检测模型、OCR 识别模型 |
| 可调整参数 | 不一定换算法，而是调策略 | 告警阈值、连续帧数量、检测区域、告警冷却时间 |
| 不建议修改 | 可以解释，但不鼓励小白修改 | 数据输入格式校验、基础预处理、结果格式化 |
| 需要专家确认 | 可以给建议，但要提示风险 | 多模型融合策略、复杂时序判断、边缘端部署优化、跨摄像头跟踪 |

---

## 三、当用户想换某一步时，系统应该先“翻译用户意图”

用户可能不会说：

> 替换人员检测模型。

他可能会说：

- 这个人员检测能不能换个？
- 不用识别人可以吗？
- 有没有更便宜的办法？
- 这个是不是太复杂了？
- 我只想知道有没有人，不需要那么准。
- 如果晚上看不清怎么办？
- 人员检测有没有别的方案？

系统要先判断用户真正想改的是哪类诉求。

| 用户表达 | 实际意图 |
|---|---|
| 换成人脸识别行不行？ | 想替换识别目标 |
| 有没有更快的？ | 想降低延迟 |
| 能不能便宜点？ | 想降低成本 |
| 晚上能用吗？ | 想适配低光场景 |
| 误报太多怎么办？ | 想提升准确率 |
| 不用这个步骤可以吗？ | 想删除或简化节点 |
| 有没有别的办法？ | 想看替代方案 |

系统不应该直接回答“可以”或“不可以”，而是应该先说清楚：

> 你想调整的是“人员检测”这一步。它负责先从画面里找到人。这个步骤可以替换，但如果完全去掉，后面的动作判断就没有对象了。

---

## 四、替代方案要按小白决策方式展示

错误展示方式：

```text
可替换为：
1. YOLOv8
2. RT-DETR
3. Faster R-CNN
4. OpenPose
```

小白用户看不懂。

正确展示方式：

```text
你可以从这几种方向里选：

1. 更快的人员检测
适合：摄像头多、需要实时告警。
优点：响应快，部署成本低。
代价：远距离、小目标可能漏检。

2. 更准的人员检测
适合：误报漏报要求很低的场景。
优点：识别更稳。
代价：需要更好的显卡或云端算力。

3. 人脸/人体特征识别
适合：不仅要知道“有人”，还要区分“是谁”。
优点：能做身份判断。
代价：涉及隐私合规，且对画面清晰度要求更高。

4. 区域变化检测
适合：只关心有没有物体进入区域，不关心是不是人。
优点：简单、便宜。
代价：容易把动物、光影、车辆也当成异常。
```

这样用户不用懂模型名，也能做选择。

---

## 五、每次替换都要展示“影响范围”

用户选择替换后，系统应该告诉他：

1. 替换了什么。
2. 为什么这样替换。
3. 会影响哪些后续步骤。
4. 有什么风险。
5. 是否需要补充信息。

例如用户把“人员检测”换成“区域变化检测”：

```text
已将“人员检测”替换为“区域变化检测”。

这样做的好处：
- 实现更简单。
- 算力要求更低。
- 适合只判断“有没有东西进入区域”的场景。

需要注意：
- 它不再能确认进入的是不是人。
- 后面的“人员动作判断”将无法继续使用。
- 如果你仍然需要判断人的行为，建议保留人员检测。
```

然后系统应该主动给出下一步：

```text
你可以选择：
1. 只保留区域入侵告警。
2. 改成“先区域变化检测，再做人形确认”。
3. 继续保留原人员检测，只换成更快的模型。
```

## 六、流程图应该是“可理解的流程图”

建议前端把流程拆成四类节点。

### 1. 输入节点

例如：

- 摄像头视频流
- 上传图片
- 历史视频
- 传感器数据

### 2. 感知节点

负责“看见什么”：

- 人员检测
- 车辆检测
- 烟雾检测
- 火焰检测
- 安全帽检测

### 3. 判断节点

负责“理解发生了什么”：

- 行为判断
- 越界判断
- 时序判断
- 多帧确认
- 规则判断

### 4. 输出节点

负责“结果怎么用”：

- 告警推送
- 截图留证
- 结构化记录
- 大屏展示
- API 输出

这样小白可以理解：

> 先输入数据，再看见目标，再判断事件，最后输出结果。

---

## 七、推荐的用户交互流程

### 第一步：生成初始流程

系统给出：

```text
我先把方案拆成 5 个步骤，你可以点任何一步查看解释或修改。
```

流程图：

```text
摄像头视频
  ↓
识别画面里的人
  ↓
判断人的动作
  ↓
连续多帧确认
  ↓
触发告警
```

### 第二步：用户点“识别画面里的人”

右侧或聊天区展示：

```text
这一步负责从画面中找到人，是后续动作分析的基础。

你可以修改它：
- 想更快
- 想更准
- 想更便宜
- 想换成别的识别对象
- 想去掉这一步
```

### 第三步：用户说“有没有别的可以替换？”

系统回答：

```text
可以。你可能想换的是“人员检测”这一步。下面是几个替代方向：
...
```

### 第四步：用户选择一个替代方案

例如：

```text
选更便宜的。
```

系统更新流程图，并解释影响。

### 第五步：系统重新检查流程是否合理

如果替换导致后续节点失效，系统要提示：

```text
你选择的方案会影响“动作判断”这一步，因为区域变化检测无法判断人的动作。

我建议改成：
区域变化检测 -> 人形二次确认 -> 告警输出
```

## 八、`tool_orchestration_agent` 的角色定义

建议将 `tool_orchestration_agent` 定位为：

> 面向用户确认后的方案，把算法方案转成可理解、可编辑、可替换、可验证的流程编排。

它内部可以分成 5 个子能力：

1. 流程拆解
   把方案拆成用户看得懂的步骤。

2. 节点解释
   解释每个步骤的作用、输入、输出和必要性。

3. 替代推荐
   根据用户目标推荐替代方案。

4. 影响分析
   判断替换后会不会影响上下游。

5. 重新编排
   根据用户选择更新流程。

---

## 九、关键设计原则

### 1. 不问“你要换成什么”

小白不知道能换成什么。

不要问：

```text
你要把人员检测换成什么？
```

应该问：

```text
你是想让它更快、更准、更便宜，还是适应特殊场景？
```

### 2. 不直接展示模型名

先展示用户价值，再展示技术名称。

```text
更快的方案：轻量人员检测模型
技术选型：YOLOv8n / YOLOv10n / PP-YOLOE-s
```

### 3. 不让用户承担系统设计责任

不要问：

```text
你想怎么编排？
```

应该问：

```text
你更在意实时性、准确率、成本，还是部署简单？
```

### 4. 每次修改都要有解释

小白用户需要知道：

```text
为什么这样改？
改完有什么好处？
有什么代价？
下一步还能怎么调？
```

## 十、最终理想体验

用户说：

```text
我觉得人员检测这一步能不能换掉？我也不知道换成什么。
```

系统应该回答：

```text
可以，我先帮你解释一下。

“人员检测”这一步的作用是从画面里找出人。后面的动作判断、越界判断、告警确认都依赖它。

如果你想换掉它，通常有 4 个方向：

1. 换成更快的人员检测
适合摄像头多、需要实时告警的场景。

2. 换成更准的人员检测
适合误报漏报要求高的场景。

3. 换成区域变化检测
适合只关心有没有东西进入区域，不关心是不是人。
但它不能判断人的动作。

4. 换成人脸/身份识别
适合需要知道具体是谁的场景。
但会增加隐私合规要求。

如果你不确定，我建议选择“更快的人员检测”，因为它对原流程影响最小，只是优化这一步，不会破坏后面的动作判断和告警逻辑。
```

---

## 总结

对小白用户最友好的算法流程编排方式是：

> 先解释，再翻译诉求，再给选择，再说明影响，再帮他完成修改。

`tool_orchestration_agent` 的核心价值不只是“生成流程”，而是帮助用户理解流程、修改流程，并降低用户参与算法方案设计的门槛。
